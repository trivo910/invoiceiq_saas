# Billing and plans

Phase 4 implementation status: configurable billing foundation is implemented. Commercial values and a few lifecycle rules remain open, so paid checkout and any behavior that depends on those values stay unavailable until configured. See the current position in `PROGRESS.md`.

## Plans and entitlements

Configurable plan records exist for Existing workspace, Free trial, Starter, Pro, and Business. Prices are stored in paise and limits/features on `plans`; paid plan rows start inactive and blank until product values and matching Razorpay plan IDs are supplied. A null limit means no limit is applied. No prices or quotas are seeded. The trial duration is 14 days by default (`BILLING_TRIAL_DAYS`) and new registrations receive a trial subscription. The setting must be a non-negative integer: malformed or negative values stop registration before any workspace data is written. Zero explicitly means no trial period (the trial expires at registration time). Migrated workspaces keep an unlimited Existing workspace subscription to preserve access.

## Trial and payment lifecycle

The trial does not require a card. Razorpay subscription creation uses server-side credentials and plan IDs, interval-specific configured cycle count, then redirects to the provider-hosted short URL. Checkout creation locks the workspace row, rechecks for an existing pending subscription, and reuses that checkout instead of creating a duplicate during concurrent requests. If an older pending row has no usable hosted URL, checkout fetches the existing provider subscription and repairs its saved URL when the provider confirms the matching subscription ID. Provider API requests time out after 10 seconds. The configured Razorpay plan is fetched and its amount, currency, and interval are compared with the local plan before checkout. The provider subscription response must contain an ID and a hosted `https://rzp.io/` URL before a pending row is saved, preventing malformed responses from leaving an unusable local checkout. The browser return is not proof of payment. `POST /webhooks/razorpay` verifies HMAC against raw request bytes, requires the provider event ID, records it uniquely, and processes events idempotently. Unique provider payment IDs also prevent duplicate payment or tax invoice records when the same capture is reported in distinct events; once captured, a payment's amount, currency, method, and paid timestamp are preserved if a later capture notification conflicts. If an event references a subscription not yet persisted locally, the endpoint returns `503` without consuming the event so Razorpay can retry; this covers the race between provider subscription creation and the local database insert. Provider event timestamps prevent an older subscription-state event from overwriting a newer one; payment history from stale events is still retained. Invalid or non-positive provider period timestamps are ignored so they cannot erase a valid paid-through date. Invalid payment timestamps use webhook receipt time. A failure webhook that references a payment already marked captured cannot downgrade its payment record or subscription state. GST invoices are created only for positive INR captures whose amount matches the configured subscription cycle price, including GST for exclusive pricing. Captures in another currency, for zero, with a mismatched amount, or without valid currency metadata remain in payment history without an INR tax invoice; missing/invalid currency is stored as `XXX`. Activated/charged/resumed events activate the subscription; `payment.failed` and pending events enter `past_due` only after an established subscription fails. The first provider failure timestamp is retained separately from the latest provider state timestamp, so repeated failures while grace is unset do not shift a grace deadline when policy is configured later; a successful activation clears this past-due origin. Missing/invalid failure timestamps anchor to webhook receipt time. A `subscription.halted` event on an initial pending checkout marks that checkout `checkout_failed` without replacing the existing trial/legacy entitlement, releases the pending-checkout lock, and allows the owner to retry. Late pending/failure callbacks cannot turn this terminal initial-checkout state into a past-due entitlement, but a valid failed payment attempt remains in billing history. A halted event for an established subscription continues through the normal past-due/grace behavior. Paid `active` subscriptions require a confirmed future period end to retain write access; a missing period end is treated as ended, while the explicit legacy plan remains unlimited. A paused subscription keeps write access through its paid period end and becomes read-only after it; a newer resumed event restores active status. Cancellation and completion preserve access through their provider period end when supplied. Captured subscription payments and failed renewal attempts are retained in tenant-scoped history; failures do not issue invoices. The webhook resolves tenant context from the matched provider subscription, not the browser/request tenant.

When calculating a grace deadline from configuration, `BILLING_GRACE_DAYS` must be a non-negative integer; malformed or negative values raise an explicit configuration exception instead of silently expiring access. Zero means the grace deadline is the original failure time. If unset, no grace deadline is derived and writes remain available pending the product decision.

Configure plan rows and Razorpay plan IDs in MySQL after setting `RAZORPAY_KEY`, `RAZORPAY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `RAZORPAY_MONTHLY_CYCLE_COUNT`, and `RAZORPAY_YEARLY_CYCLE_COUNT`. Checkout remains disabled unless price, matching provider plan ID, active flag, all feature flags, API credentials, a non-whitespace webhook secret, interval cycle count, nonblank seller identity/tax fields, a valid GST rate, SAC, and `BILLING_PRICE_TAX_MODE` are set. Seller name, GSTIN, PAN, address, state code, and SAC must be nonempty after trimming; GST rate must be greater than zero and at most 100. The same centralized validation prevents tax invoice issuance when seller details are blank or invalid. Requiring the webhook secret prevents customers from entering checkout when signed payment/lifecycle callbacks cannot be authenticated. Blank or whitespace-only secrets also disable pending checkout recovery and webhook processing. The tax mode is `inclusive` (catalog price includes GST) or `exclusive` (GST is added to the catalog price). Checkout fetches the Razorpay plan and verifies the exact gross amount, INR currency, and billing interval before creating a subscription. A pending checkout does not replace the current trial/legacy subscription. Cycle counts are capped at 1,200 monthly or 100 yearly cycles, matching Razorpay's documented 100-year maximum subscription duration.

## Status state diagram

If a webhook reuses a provider payment ID already bound to a different tenant or subscription, or its subscription and payment entities identify different subscriptions, the event is logged and marked processed without changing the existing payment, issuing an invoice, or applying the conflicting subscription transition.

```text
trialing --trial expires/subscribe--> active
trialing --trial expires/no payment--> expired (read-only)
pending --provider halted before activation--> checkout_failed (retry allowed; prior entitlement unchanged)
active --payment failure--> past_due (grace period)
past_due --payment succeeds--> active
past_due --grace expires--> read_only
active --cancel requested--> cancel_at_period_end --> cancelled
active --provider completion--> completed
```

Data is never removed when a subscription expires or fails. The billing page, authorized settings/member-list pages, and reads/exports remain accessible. Subscription write enforcement is applied to mutations, not those read-only pages. The subscription middleware blocks writes when a trial ends, a configured grace period expires, or a subscription ends. Once a configured grace period has expired, the workspace can start a replacement checkout to restore access; a checkout is not offered while grace access remains active. An active paid subscription whose recorded period is missing or elapsed can also start replacement checkout, covering a missed provider terminal event; a current paid period remains protected, and legacy workspaces retain unlimited access while remaining eligible to upgrade. When grace is unset, `past_due` retains write access until a product decision is supplied; when grace is configured, its deadline is anchored to the provider's failure event timestamp (or webhook receipt time only when the provider timestamp is missing/invalid), so delayed webhook delivery cannot extend the access window. If grace is configured after a failure was recorded, the deadline is derived from the original provider failure timestamp rather than starting a fresh grace window. Set `BILLING_GRACE_DAYS` before production. Invoice and member seat limits are checked at the route and rechecked while locking the tenant row during invoice creation/invitation/acceptance to prevent concurrent over-limit writes. Outstanding unexpired invitations reserve member seats; expired invitations do not, and resending an existing invitation reuses its reserved seat.

## Billing UI and operations

When a legacy pending checkout row lacks a hosted URL, the owner billing page offers a restore action. It fetches the existing provider subscription and only saves the URL if the provider confirms the same subscription ID. Existing pending checkout URLs are hidden and the checkout endpoint refuses continuation when webhook authentication is missing or the tenant state code is blank/whitespace-only; the billing page explains the prerequisite and leaves the pending state and current entitlement unchanged. A past-due notice shows the calculated grace deadline when available; with no configured grace duration, it clearly says write access remains enabled while the policy is unset.

The billing page, checkout actions, and subscription invoice downloads are owner-only based on the active workspace membership. It shows the current plan/status, trial or renewal date, usage, configured plan choices, payment history, and private tenant-scoped invoice PDF downloads. Plan cards use responsive grid sizing, allow descriptions to wrap, and wrap checkout button labels on narrow screens. Status and read-only messaging follow the same trial/period/grace rules as write middleware, so an expired trial or period does not continue to appear active. Paused, cancelled, and completed subscriptions keep writes available through the provider's final paid period end, then become read-only; replacement checkout is allowed for paused subscriptions only after their paid period ends. Upgrade checkout is available only for active paid plans with a positive price and complete provider configuration; the free trial and legacy plan cannot be purchased through Razorpay. Downgrade, active subscription changes, cancellation requests, proration, and refunds remain unavailable until product decisions exist.

Subscription invoice PDFs are issued only when seller name, GSTIN, PAN, address, state code, GST rate, SAC, tax mode are configured, and the tenant has a state code. State-code whitespace is trimmed before checkout eligibility and same-state classification. The invoice gross equals the amount actually captured; inclusive mode derives the taxable subtotal from that gross, while exclusive mode uses the catalog base price. Same-state invoices split GST into CGST/SGST with any rounding remainder assigned to SGST so the components equal total tax; other-state invoices show IGST. Seller/buyer details are snapshotted at issue time, with trimmed state codes in the saved tax invoice. Configure the correct seller/tax treatment for the actual SaaS entity before enabling this in production.

## Phase 5 administration boundary

Platform admins can edit quotas/entitlements and maintain the plan catalog. Once referenced, a plan's code/prices/provider IDs cannot be rewritten; use a new plan for new pricing. System/referenced plans cannot be deleted. Manual grants create local active access with an explicit deadline and no payment/provider action; outstanding provider subscriptions and remaining cancelled/completed paid access block grants. Provider-managed changes still await Phase 4 policy and QA. Manual grants are excluded from the platform catalog MRR estimate.

Coupon codes are managed as a validated platform catalog only. They do not alter checkout/payment/invoice amounts and have no redemption flow until discount and provider rules are approved. Suspended tenants cannot write or use tenant routes, but signed provider events continue to be processed. None of these controls resolves the current Razorpay support issue or production commercial decisions.
