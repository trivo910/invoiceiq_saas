# Architecture decision log

| Date | Decision | Reason | Alternatives rejected / status |
|---|---|---|---|
| 2026-10-23 | Keep Phase 0 documentation-only; implement Phase 1 only after user says to continue | User explicitly requires one phase per response and approval before Phase 1 | Starting schema/code changes in Phase 0 was out of scope; the user later approved by directing continuation |
| 2026-10-23 | Treat static migrations as current schema evidence, and label production state unknown | Repository scan cannot reveal deployed drift or live records | Claiming live schema/data based only on migrations would be unsafe |
| 2026-10-23 | Document shared-schema, single-database tenant architecture as target | Explicit SaaS requirement and shared-host constraint | Separate database per tenant is not the requested design |
| 2026-10-23 | Preserve current GST and invoice-entry logic as protected behavior | Existing GST logic and Odoo-style inline UX must not be rewritten during conversion | Reimplementing tax math in tenancy foundation risks regressions |
| 2026-10-23 | Treat subdomain tenant resolution as deferred and off by default | Explicitly requested optional later phase | Host-header-based tenant selection is not needed for foundation |
| 2026-10-23 | Use a `tenant_user` pivot for workspace membership and per-workspace role | Supports team members and future multiple workspaces per identity without changing users uniqueness | `users.tenant_id` would constrain each identity to one workspace |
| 2026-10-23 | Until workspace switching exists, resolve a user's lowest-ID tenant membership | Existing app has no workspace selector; deterministic fallback preserves access for migrated users | Host/subdomain selection remains deferred and off |
| 2026-10-23 | Generate new numbers as `PREFIX-YYYY-YY-NNNN` based on tenant FY start; retain old numbers | Makes the sequence tenant/FY scoped while keeping a recognizable invoice prefix | Calendar-year sequence is replaced for new invoices; existing numbers are never rewritten |
| 2026-10-23 | Set MySQL as default and configure Laravel database queue with DB tables | Matches shared-host/VPS constraints and removes silent SQLite default | Redis/Horizon/daemon-based queue processing is outside the target |
| 2026-10-23 | Verify new accounts while marking migrated users verified and tenants onboarded | Prevents new access gates from interrupting existing installations | Requiring legacy users to verify without configured email could lock them out |
| 2026-10-23 | Store invitation tokens as SHA-256 hashes with seven-day expiry and keep roles on `tenant_user` | Limits leaked-token impact and keeps permissions workspace-specific | A global user role cannot represent different access across workspaces |
| 2026-10-23 | Use Laravel Gates for Phase 2 write/delete/workspace boundaries | Shares authorization decisions across route groups using active membership roles | Full per-model policy coverage is deferred to broader authorization work |
| 2026-10-23 | Enforce same-tenant links in request validation and model save guards for the existing customer/invoice/item/payment relations | Existing nullable `ON DELETE SET NULL` relations make composite foreign keys a behavior-changing migration; current scope validation closes cross-tenant writes without changing delete behavior | Composite constraints can be reconsidered in a future schema redesign with explicit nullability semantics |
| 2026-10-23 | Use a separate MySQL `invoiceiq_test` database for feature tests | Exercises MySQL enums/DDL and prevents test refreshes from touching local application records | SQLite in-memory tests are not representative of the supported production schema |
| 2026-10-26 | Leave billing prices, quotas, seller tax details, grace duration, downgrade/proration/refund policy unset until the product owner supplies values; disable checkout and invoice issuance until configuration is complete | The Phase 4 billing spec explicitly marks these as open decisions and says not to invent them | Temporary code defaults could create incorrect charges or tax invoices; unset feature flags remain allowed until decided |
| 2026-10-26 | Add an explicitly temporary local/testing billing demo catalog and seven-day grace assumption; preserve data and block over-limit writes on downgrades, leave proration disabled, and handle refunds manually in the sandbox; block checkout and tax invoice issuance in demo mode | User requested dummy values to continue Phase 4; the values support UI and policy-flow development without representing approved commercial or tax terms | Production still requires product-owner values; seller tax identity remains unset; demo mode is ignored outside local/testing |
| 2026-10-26 | Track the latest provider state-event timestamp on each subscription and ignore older state transitions | Webhook retries/delays can deliver events out of order; this prevents stale failures or activations from regressing newer state while still allowing payment history to be recorded | Events without a provider timestamp continue to process in arrival order |

| 2026-10-28 | Use a separate super_admins identity table/provider/session guard, provisioned by an interactive hidden-password command | Tenant role strings/registration must never confer platform access; no default admin secrets | Reusing the legacy users.role admin value is unsafe |
| 2026-10-28 | Make owner impersonation read-only, pinned to one active/onboarded workspace, with 15-minute request-enforced expiry and full start/end audit | Meets support inspection needs while preventing billing/account changes and tenant switching | Unrestricted owner writes and indefinite sessions were rejected |
| 2026-10-28 | Keep provider-managed plan changes and coupon redemption behind unresolved Phase 4 policies; offer explicit local time-limited grants and catalog CRUD | Allows independent Phase 5 controls without inventing payment/proration/discount behavior | Do not shadow an outstanding provider subscription or rewrite referenced price contracts |
